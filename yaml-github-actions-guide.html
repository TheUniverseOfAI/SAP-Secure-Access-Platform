1. What YAML is

YAML ("YAML Ain't Markup Language") is a plain-text format for writing structured data — the same kind of data you could write as JSON, just designed to be easier for a human to read and edit by hand. Where JSON uses { }, [ ], and lots of quotes and commas, YAML uses indentation and line breaks to show structure, closer to how you'd naturally outline a document.

Here's the exact same data in both formats:

JSONYAML
{
  "name": "sap-web",
  "scripts": {
    "build": "vite build"
  },
  "keywords": ["react", "vite"]
}
 
name: sap-web
scripts:
  build: vite build
keywords:
  - react
  - vite

YAML isn't specific to GitHub — it's a general-purpose format used all over software tooling: Docker Compose files, Kubernetes configs, CI pipelines (GitHub Actions, GitLab CI, CircleCI), and plenty of app config files all use it. Learning YAML syntax once transfers everywhere.

2. YAML syntax — the five things you need

1. Key: value pairs

name: Deploy to GitHub Pages

A colon-and-space separates the key from its value. That's it.

2. Nesting via indentation

This is the part that trips people up most, so slow down here. In YAML, whether something is "inside" another thing is decided purely by how many spaces come before it — there are no braces, no brackets, nothing else marking the boundary. 

permissions:
  contents: read
  pages: write

contents and pages both sit 2 spaces in, so YAML reads them as two children of permissions — i.e. "permissions has a contents setting and a pages setting." If pages were indented differently, it would no longer belong to permissions at all.

Indentation depth = how deeply nested something is

Here's a bigger piece of your actual file, with each indentation level marked on the left so you can see how depth maps to "belongs to what":

L0jobs:
L1build: 2 spaces in → a child of jobs. Specifically, jobs now has one entry named build.
L2runs-on: ubuntu-latest 4 spaces in → a child of build. Says what build runs on.
L2steps: Also 4 spaces in → a sibling of runs-on, same level, also a child of build.
L3- uses: actions/checkout@v4 6 spaces in → the first item in the steps list.
L3- run: npm ci Same depth as above → the second item in that same list.

Read it top to bottom as: "jobs has a build. build runs on ubuntu-latest and has steps. steps is a list, and its first two items are checkout and npm ci." Each extra 2-space indent means "one level deeper inside the thing above it."

The rule that matters most: things at the same "level" of a list must line up at exactly the same column. If two lines are supposed to be siblings (like runs-on and steps above, both children of build) but one is indented 4 spaces and the other 5, YAML doesn't error out politely — it just reads a different structure than you meant. This is, by a wide margin, the most common YAML mistake.
Practical tip: don't count spaces by eye. Use an editor that shows indentation guides (VS Code does this by default — you'll see faint vertical lines connecting each indentation level), and let it auto-indent when you press Enter after a : or a -. Also: always use spaces, never Tab — YAML forbids tabs for indentation entirely, and most editors already convert Tab to spaces automatically for .yml files.

3. Lists

branches: [main]

# the same list, written the "long" way:
branches:
  - main

A dash (-) marks each item in a list. Square brackets are a shorthand for short lists on one line — both forms mean the same thing.

4. Strings usually don't need quotes

node-version: 22       # a number
cache: npm            # an unquoted string
GITHUB_PAGES: "true"  # quoted, to force it to be read as TEXT, not the boolean `true`

Quotes become necessary when a value could otherwise be misread as something else (like a boolean, a number, or when it contains a colon or starts with a special character).

5. Comments

# Anything after a # is a comment, ignored by whatever reads the file.
That's genuinely most of it. YAML has more edge cases (multi-line strings, anchors/aliases, explicit typing) but 95% of the files you'll encounter — including yours — only use these five things.

3. What topic this file belongs to: GitHub Actions

YAML is just the syntax. The actual topic your file is written for is GitHub Actions — GitHub's built-in automation system. A GitHub Actions "workflow" is a YAML file that tells GitHub: "when X happens in this repo, run these steps."

Your file, deploy-pages.yml, says: "when someone pushes to the main branch, build the app and publish it to GitHub Pages." That's the entire job. GitHub reads the YAML, understands the structure (jobs, steps, triggers) because GitHub Actions defines what keys are meaningful — on, jobs, runs-on, steps, uses, run are all part of the GitHub Actions "vocabulary", not YAML itself. YAML doesn't know or care what those words mean; it just parses the structure. GitHub Actions is the thing that gives that structure meaning.

Think of it like this

YAML is the grammar (how to structure sentences).
GitHub Actions is the vocabulary (what words are valid, what they mean).
Your file is a sentence written in that grammar, using that vocabulary.

4. Why the file lives at .github/workflows/

This isn't a convention you get to choose — it's a hard requirement. GitHub only looks for workflow files in exactly one place:

.github/ A reserved folder name GitHub recognizes at the root of any repo — used for repo-level GitHub configuration in general (workflows, issue templates, PR templates, funding info, etc.), not just Actions.
.github/workflows/ The specific subfolder GitHub Actions scans. Every .yml file dropped in here is automatically treated as a separate workflow — no registration step, no config pointing to it. The file's location is the registration.
deploy-pages.yml The filename itself is arbitrary — you could call it banana.yml and it would work identically. It's just named descriptively so a human skimming the folder knows what it does. If your repo grows more automation later (running tests on every PR, for example), that would be a second, separate file in the same folder — e.g. test.yml.

So to directly answer "why this path": because GitHub Actions only discovers workflows by scanning .github/workflows/*.yml in your repo. There's no other way to tell GitHub about a workflow.

5. Line-by-line walkthrough of your actual file

Here's exactly what's in .github/workflows/deploy-pages.yml in this repo, and what each part does.

Trigger: when does this run?

on: push: branches: [main] workflow_dispatch:
Two ways this workflow can start: automatically, whenever a commit lands on main (e.g. after merging a PR) — or manually, by clicking "Run workflow" in the GitHub Actions tab (workflow_dispatch). This matches what you chose earlier: auto-deploy on every push to main.

Permissions & concurrency

permissions: contents: read pages: write id-token: write
By default, an Actions run gets minimal access. This grants exactly what's needed: read the repo's code, and write to GitHub Pages. id-token is needed for GitHub's secure Pages-deployment handshake.
concurrency: group: pages cancel-in-progress: true
If you push twice in quick succession, this cancels the older, now-outdated deploy in favor of the newer one, instead of letting them race and potentially publish an older build last.

Job 1: build

jobs: build: runs-on: ubuntu-latest
Defines a job named build. GitHub spins up a fresh, temporary Ubuntu Linux virtual machine to run it on — every workflow run starts from a clean slate.
steps: - uses: actions/checkout@v4
uses pulls in a reusable action someone else published — here, the official one that clones your repo's code onto that fresh VM (equivalent to running git clone).
- uses: actions/setup-node@v4 with: node-version: 22 cache: npm
Installs Node.js 22 on the VM (matching what this project needs) and caches installed npm packages between runs so future builds are faster.
- run: npm ci
run (as opposed to uses) means "run this literal shell command." npm ci installs your exact dependency versions from package-lock.json — the CI-safe equivalent of npm install.
- run: npm run build env: GITHUB_PAGES: "true"
Runs your project's normal build script, with one extra environment variable set. This is the same GITHUB_PAGES flag referenced in vite.config.ts — it's what tells Vite to prefix asset URLs with /SAP-Secure-Access-Platform/ instead of just /, since GitHub Pages serves this project from that subfolder path.
- run: cp dist/index.html dist/404.html
GitHub Pages can't do server-side URL rewriting. Without this, refreshing the browser on a deep link like /profile/personal would 404, because there's no real file at that path — only your JavaScript router knows about it. Serving the same index.html for the 404 case lets your app boot normally and read the real URL itself.
- uses: actions/configure-pages@v5 - uses: actions/upload-pages-artifact@v3 with: path: dist
Two official GitHub actions: one configures the Pages deployment settings, the other packages your built dist/ folder into an "artifact" — a zipped bundle GitHub can hand off to the next job.

Job 2: deploy

deploy: needs: build runs-on: ubuntu-latest environment: name: github-pages url: ${{ steps.deployment.outputs.page_url }}
A second, separate job. needs: build makes it wait for the first job to finish successfully. environment links this run to GitHub's "github-pages" deployment environment, which is what makes the live URL show up on your repo's homepage and in the PR checks.
steps: - id: deployment uses: actions/deploy-pages@v4
The actual publish step — takes the artifact from the build job and makes it live at your GitHub Pages URL.
Why two separate jobs instead of one? Splitting build and deploy is a common pattern: it keeps the "untrusted" build step (running your code, your dependencies) cleanly separated from the "trusted" deploy step (which has write access to Pages), and each job gets its own clean VM.
